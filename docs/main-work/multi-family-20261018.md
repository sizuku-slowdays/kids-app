## 家系図の見え方の問題

同じ家庭に入っている限り、APIは登録者が祖母かママかで人物を隠さない。合成データで祖母作成・ママ作成の2人物を両アカウントが同じAPI結果で受け取ることを確認。

実際の原因は未特定。家庭IDの不一致、アプリ許可/表示設定、HOME本人との紐付け、基準人物から切れたグラフ、近い親戚だけを表示する範囲、端末の古い表示を切り分ける。監査では人物名を表示せず家庭別/登録者別件数と、各本人の基準人物・非連結件数を調べる。バックアップにデータがあることと、端末で正しく表示されることは別確認。

人物の統合・移動・再登録・公開拡大は実施しない。もし必要と分かった場合は対象・件数・バックアップ・復元案を先に提示して確認を取る。

## 権限の目標（実装前の設計）

| 権限 | 対象と許可 |
| --- | --- |
| ファミリー管理 | 所属家庭の設定・招待・必要アプリ有効化。新規作成者が取得。全家庭の管理権限ではない |
| 保護者／金融管理 | 指定家庭・指定子どもの管理を明示付与。大人属性だけで取得しない。ママの既存管理を維持 |
| 一般メンバー | 本人に許可されたアプリと共有情報のみ。祖父母はこの役割＋プレゼント送信許可を基本とするが、実roleは監査後に確認する |
| 子ども | 自分の許可されたデータ。保護者による代理HOME設定は対象子どもへの権限を再確認する |
| 共有グループ管理 | 当該グループの招待・共有対象・参加停止のみ。他家庭の通帳/家計簿/子ども管理は与えない |

既存membershipsのroleを一括変更しない。既存家庭に互換モード、新規家庭に明示権限を持たせ、アプリごとのcapability（管理/閲覧/プレゼント等）を段階導入する案。権限判定はAPIとDB側の承認/金融トリガーで揃える。古いroleを残したままAPIだけ変更するとDB view/triggerと不一致になるため、gift_guardians等も同時に試験する必要がある。

既存5人に権限変更が必要なら、現状→提案→対象ID（私的管理）→影響を個別にレビューし、利用者確認前は適用しない。新家庭参加時に口座・ポイント・子どもプロフィールを自動作成しない。アプリを有効化することと金融開始操作を分ける。

## 招待設計

- 新規家庭作成／既存家庭参加／共有グループ参加をサーバー側purposeで分ける。新規家庭招待の発行権は運営または明示許可者に限定し、自由登録を開放しない。
- 高エントロピートークンはハッシュだけ保存。期限、1回使用（将来回数制限へ拡張）、取消、発行者・実行者・参加先・操作日時の監査履歴を持つ。
- URLは可能ならfragmentで渡し、ログ/Refererへ残さない。プレビューGETは消費も権限変更もしない。認証と参加先・役割の確認後にPOSTで承諾する。
- 既存アカウントで承諾できる。新規利用者だけ個人登録する。招待先役割はDBに固定し、リクエストのrole/user_idを信頼しない。使用回数の更新と所属作成を単一D1 transaction/batchで検証し、取消との競合・二重POSTを扱う。
- 最初は同一トークン1回の招待を優先。旧招待・既存端末は自動失効しない。退出/取消後のデータ取得・通知・R2を毎回現時点の所属で拒否する。

## カレンダーの移行方針

1. 現行calendar-dbの単一家庭設定は「既存予定の旧方式適用先」として保存。id=1を書き換えて別家庭へ再バインドしない。
2. 本人識別はHOME IDを正本とし、旧home_calendar_links/member_id/予定所有者は保持。新家庭の本人連携をoperator限定の手作業にしない。
3. 家庭とsharingの許可された所属をHOMEから内部Service bindingで伝え、calendar-workerが毎回検証。内部の全家庭ディレクトリを一般画面に返さない。
4. 旧予定に権限の行がなければ従来の家庭限定ルールを維持。「all」を全利用家庭へ拡張しない。
5. 新しい親族共有カレンダーだけ、明示的な参加/承諾と予定ごとの公開範囲を使う。検索・繰り返し・Google予定・通知対象・脱退後の配信で同じ閲覧判定を使う。
6. HOME→calendar-worker→notification-center-apiの対応版を確認し、未対応Workerには新機能をフェイルクローズ。既存通知を一律停止しない。

HOMEとcalendar-workerの双方に変更が必要。カレンダーWorkerは手貼りデプロイ運用のため、実際のコードバックアップと固定SHA照合を反映前に行う。

## HOME直接編集の方針

- 本人の既存user_appsとhome_preferencesを初期値にする。保存前はメモリー上のドラフト、完了で表示/順番/お気に入りを一括原子保存。キャンセル・再読込時は未保存として扱う。
- 1つのアプリの所属区画を「よく使う」「一覧」「非表示」として操作。お気に入りを通常一覧と重複させない。旧設定を初期化しない。
- 長押し開始＋Pointer Eventsでタッチ/マウスに対応。通常のスクロールと区別し、ドラッグ先をハイライト、キャンセル/範囲外ドロップ/オートスクロールを扱う。
- タップで「よく使うへ」「一覧へ」「非表示」「このカードの前へ」を用意。↑↓だけに頼らず、キーボード/支援技術でも同等操作を行えるようにする。
- revisionと許可されたアプリ集合をサーバーで照合。別ユーザー、権限が失われたアプリ、重複ID、保存途中の失敗、別端末競合を検証する。
- 子どもの代理編集は指定保護者のみ。個人HOME設定を家庭共通設定へ置き換えない。非表示を利用権限の解除と混同しない。
- 動作確認後に祖父母専用presetと旧チェック/↑↓UIを整理。固定外部リンクはデータ保存があるかを確認し、利用許可のあるアプリだけへ移す。
