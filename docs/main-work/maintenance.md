# 管理資料の更新手順

## 別のWorkで引き継ぐとき

1. このフォルダーのREADME→apps→workers→specifications→backlogを読む。
2. GitHubの各ブランチ先頭を再取得する。台帳の調査版より新しい変更と未反映の作業を確認する。
3. 対象アプリの正本と保存先を確認する。HOMEはfeat/home-auth-foundation、静的アプリはmainの調査結果を出発点にし、現在のデプロイ元は別途照合する。
4. 対象コードと関連Worker／SQLを読み、既存データ・既存URL・本人権限を保持して改修する。
5. 関連する管理資料を改修と一緒に更新する。別ブランチの場合も、mainの本台帳へ更新を反映して引き継ぎ入口を維持する。

## 改修が完了するたびに

| 変更 | 更新する資料 |
| --- | --- |
| アプリ名・URL・状態・新規追加 | apps.md |
| Worker・API・binding・D1・R2・デプロイ元 | workers.md |
| 認証・権限・保存形式・テーブル・共有・UI操作 | specifications.md |
| 完了した変更・試験・反映結果 | history.md |
| 残作業・制限・未確認・解消した項目 | backlog.md |
| 管理場所・調査対象ブランチ | README.md |

同じ変更のPR／コミットに含めるのを基本とする。HOME作業ブランチの変更は対象コードをmainへコピーせず、台帳にブランチ・コミットリンクを記載して追跡する。資料更新だけのためにWorkerを再デプロイしない。

履歴には日付（JST）、具体的な変更、リポジトリ／ブランチ、コミット、関連ファイル、検証と結果、本番反映の確認区分を記載する。ソースにある実装、利用者の報告、実環境での確認を分ける。失敗や未完了はbacklogにも残す。

## 記録テンプレート

```text
日付（JST）：
アプリ／Worker：
リポジトリ・ブランチ・コミット：
変更内容：
関連ファイル：
データ・URL・権限への影響：
検証方法と結果：
本番反映（確認済み／未確認、対象版）：
残作業：
```

確認できない項目は「未確認」。ファイル名やURLからDB名・本番稼働を推測しない。秘密値・個人データ・実データ入りのバックアップを公開資料へ貼らない。
