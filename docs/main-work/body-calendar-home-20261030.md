# からだカレンダー：不具合修正とHOME連携の次段階

2026-10-30 JST。静的画面の基準はmain a030305dddfef522dd27cbd3fe55feffcee4e316、HOME/calendar-workerの確認基準は8235388019f27d409b542fd539456adc75a32b30。

## 確認した不具合と今回の画面修正

初回ホームはrenderHomeの早期returnにより「きろくを追加」のイベント登録が実行されなかった。renderTabで描画直後に登録する。
ログイン以外の多くの操作が /api/records, /api/requests等を呼ぶが、既存calendar-workerの対応ルートは /karada/records, /karada/requests等。画面の全呼出先を既存実装へ揃える。Worker自体の変更は行わない。
loadDataのcatchが失敗を隠して記録なしに見せていたため、エラーを表示してthrowする。保存・お願い送信の失敗時は入力を残し、HTTP状態付きで画面に表示。ボタンを処理中無効化し、成功後だけ画面を進める。保存後の再読込だけ失敗した場合は「保存済み、再登録しない」を案内する。お願い成功は管理画面の一覧で確認できることを表示し、プッシュ送信とは表示しない。
JSTの今日、終了日が開始日より前の入力、枚数/錠数、iPhone日付入力の横はみ出しも確認・調整。

検証：実画面JSのVM4件（初回ボタン、保存先/保存失敗、お願い送信/失敗、読込エラーの表示）、実calendar-workerコード＋合成D1で1件（作成・取得・編集・予測・お願い送信・管理者取得・確認）。後者の表はテスト専用の最小fixtureであり、本番schemaを確認したという意味ではない。JS構文合格。監査Python2件（個人値を出さない、別DBで停止）。実iPhoneの保存確認と本番DB schemaは利用者確認待ち。本番の記録/お願いは試験作成していない。

## HOME連携・新規利用開始（未実装・未反映）

今回の画面修正と区別する。現状は旧認証のまま。既存の本人識別方式を販売用認証として流用しない。新規の一般公開ユーザー登録を旧APIへ追加しない。

- HOMEの既存セッションで本人を認証し、HOME内の同一オリジン画面/APIを用意する。HOME→既存CALENDAR_SERVICE、calendar-worker→HOME_AUTHで本人/所属/役割を検証。クライアント選択のユーザーIDだけで本人と判断しない。
- HOMEユーザーID・ファミリーIDと既存period本人IDを、追加の連携表で明示的に結ぶ。名前や「長女/次女」から推測しない。既存記録/お願い/メモはその本人IDを維持する。
- 原家族の管理者が、既存本人の所有確認を経て既存アカウントへ紐付ける。別家庭から旧アカウント一覧や健康記録へアクセスさせない。1つの旧本人を複数のHOME本人へ重ねて登録しない。
- 新しいHOME利用者は旧本人を引き継がず、新しいからだプロフィールを作成できるようにする。子どもは保護者が必要な設定を管理し、本人用画面から自分の記録・お願いを使用する。HOMEのアカウント/招待作成基盤を使い、別の固定3人ログインや共用パスワードを増やさない。
- 既存一般メンバー・祖父母という理由だけで、姉妹の健康記録の閲覧権を与えない。保護者の対象児童を明示してAPIで検証。大人本人の私的記録と子どもの見守り範囲を分ける。
- お願い・在庫は家庭単位で分離。本人のメモは個人単位。グローバルな旧在庫は新家庭へコピー/共有しない。既存の値を無断初期化しない。
- HOME連携後は旧認証経由で同じ記録へ抜け道が残らない設計と、セッション切替/解除/家庭脱退・他家庭のID差替えの試験が必要。

## 先に必要な確認

period系CREATE TABLE定義/制約は現行リポジトリに見つからず、Workerコードで使うカラムだけを確認した。NULL可否、一意制約、ID生成、保存済み行・本人の対応は未確認。そのため今回は移行SQL/ユーザー紐付けを実行しない。

scripts/prepare-body-calendar.ps1は利用者PCでhome-dbとcalendar-dbの最新SQL exportを取り、ローカルSQLiteでintegrity/FKを確認する。summary-safe-to-share.jsonにはカラム名/型/NOT NULL/PK/一意インデックス列と件数だけを出す。氏名・ユーザーID・パスワード値・記録・お願い・実データ入りSQLは共有不要。export中にD1が一時的に照会へ応答できない可能性があるので、利用が少ない時間に行う。

確認後に追加表/権限/API/画面を実装・テストし、現行calendar-workerのバックアップとGitHub照合、反映手順、前後の件数/全旧行照合を用意する。破壊的変更や既存人物データの移動が必要なら実行前に停止する。おしゃべり等の保留作業は維持。
