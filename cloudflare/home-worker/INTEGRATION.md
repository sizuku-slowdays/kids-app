# HOMEへのアプリ接続仕様（移行前の準備）

既存アプリの改修を開始する前に使う設計資料です。この資料の保存は移行開始を意味しません。calendar-worker・既存D1・既存公開URLは変更していません。

## 現在使える境界

| 呼び出し | 認証後の用途 |
|---|---|
| GET /api/me | user.id、display_name、login_name、platform_roleと所属グループ（id/name/kind/role） |
| GET /api/home | 利用権限があるアプリの一覧。visibleは表示設定でありアクセス許可ではない |
| PUT /api/home/{app-id} | 本人のHOME表示・非表示 |
| GET /media/{file-id} | セッション、アプリ利用権限、resource所有者または承認済み共有許可を検証して非公開R2から配信 |
| GET /api/sessions、DELETE /api/sessions/{id} | 本人の端末一覧と個別失効 |
| POST /api/logout | 現在のセッション失効 |

CookieはHttpOnly/Secure/host-only。ブラウザのJSにはセッショントークンを渡しません。個人情報の取得は同じHOMEオリジンから行い、401はログインへ案内します。API・画像の応答はprivate, no-storeです。

/api/meの結果を画面表示に使うことはできますが、アプリ側サーバーはブラウザが送ったuser_id・グループID・本名・権限フラグを認証の根拠にしてはいけません。利用者IDはサーバーで検証したセッションから決定します。

## 移行時の構成

各アプリのUIとAPIをHOMEと同じオリジンのパスへ配置する構成を基本とします。ホスト名をまたいでCookieを配布する実装にはしません。

既存Workerを残す場合はHOMEを入口としてService Bindingで内部呼び出しする構成を検討します。サービス間の認証・権限照会インターフェースは未実装です。公開HTTPリクエストで偽装できる利用者ヘッダーを信用する方式は禁止です。内部呼び出しでも要求ごとにセッション失効と対象resourceのアクセス権を検証し、認証情報はログやURLへ含めません。

内部APIから既存Workerへ移す場合、旧Workerのworkers.dev URLや既存ルートを直接叩いて保護を迂回できないことが移行完了の条件です。旧URLの廃止・リダイレクト等はユーザーと確認して決めます。接続するだけでは旧URLが保護された扱いになりません。

## 所有・共有とアプリ固有データ

- 個人所有: resources.owner_user_id。個人HOMEへの表示と、データ閲覧権限を区別する。
- グループ所有: resources.owner_group_id。groups.kindはhouseholdまたはsharing。
- 他の個人・グループへの共有: resource_grants。accepted_atがありrevoked_atがない許可だけ有効。
- readとwriteを区別する。現在のcanReadは閲覧の評価のみであり、更新APIに転用しない。共有の作成・承認・取消UI、更新権限評価は対象アプリの移行前に実装する。
- 家庭をまたぐ共有は、共有元の許可と共有先の承認を確認する。管理者の役割だけで個人の非公開データを見せない。

時間割はchildrenを人数分登録し、child_idと週開始日で保存する。本人限定の時間割と保護者への共有は明示的に設定し、子どもIDをURLから受け取っただけで画像を返さない。先週・今週の週境界は日本時間・月曜開始を基本として移行時に確定する。

アルバムはアルバム単位にresourceを割り当て、画像を同じresourceへ関連付ける。家庭アルバムとゲーム共有アルバムは所有者・共有先で区別する。すべてのアルバムを家庭所属だけで一覧・取得可能にしない。

カレンダーはカレンダー単位または用途別resourceとする。通常の予定と健康等の本人限定データを同じ共有権限で開放しない。旧プロフィールとの対応はlegacy_linksに記録し、表示名での推測や旧家族一覧のハードコードはしない。

つうちょうは対象利用者IDと所有者・保護者の操作権限を対応付ける。残高や履歴の変更は画面上の利用者選択に依存せず、API側で権限を確認する。

## 1アプリごとの移行条件

1. ユーザーがHOME基盤を確認し、対象アプリの移行開始を了承する。
2. 既存データの保管先・API・画像公開元・利用者IDを確認し、バックアップと戻す手順を準備する。
3. HOMEの同一オリジンの入口、認証済み利用者取得、データの所有者とread/write判定を実装する。
4. 未認証のページ/API/画像直アクセス、別グループ、共有承認前後と取消、端末失効を検証する。
5. 旧公開経路の迂回を閉じたことを確認し、アプリのstatusをreadyへ変更する。
6. スマホとホーム画面追加で実機確認してから次のアプリへ進む。

最初の候補は「つうちょう」。現在のアプリカタログは準備中のままです。

## HOMEの確認状況（2026-10-02）

ユーザー確認済み: 親アカウントの初期登録、別ブラウザでのID・パスワードログイン、同一ブラウザで閉じて開き直した際のログイン保持、子どもプロフィールの追加。
確認待ち: 姉妹の招待登録とログイン保持、iPhoneのホーム画面追加、端末別失効の実機確認。
公開環境で未認証のGET確認済み: /と/apps/calendarと/index.htmlは303で/loginへ転送。/loginは200。/api/me・/api/home・/media/probe-no-fileは401。これらはprivate, no-store。実在画像や認証済み別グループでの検証は別途必要。
ローカル確認済み: 招待の使用済み・期限切れ、Origin検証、別グループのメディア拒否、共有承認と取消、端末別失効、ログアウト、試行回数制限。
画像の実データはまだ新R2へ移行していません。公開環境の画像権限・無料プランでの認証CPUの継続的な安定性は、実機試験だけで完了としません。

初期登録完了後はCloudflareのBOOTSTRAP_SECRETを削除可能。秘密の値を会話・GitHubへ送る必要はありません。

## 筋肉貯金（2026-10-02 接続）

`/apps/muscle-bank/` と `/api/muscle-bank/state` を同一HOMEセッションで保護。migration 0003は本人限定アプリ権限と専用テーブルを追加するだけで、既存レコードや残高は変更しない。ママの登録済み初期アカウント `bootstrap-admin` にだけ `personal_app_access` を付与。家庭所属、operatorの役割、表示名、HOME表示設定だけではアクセスできない。

新Worker/D1/R2の作成は不要。home-dbの `muscle_bank_states` を専用に使用し、home-private内の `muscle-bank/owners/{本人ID}/` に写真を保存。既存資産のキーは変更しない。画像は認証済みAPIでだけ読み出す。不要画像の自動削除はしない。

データはアカウント保存・別端末から取得可能。日付・ポイント・基金設定・画像処理は端末保存版と同じ。CookieはHOMEオリジン限定。画面・API・静的ファイル直アクセスは未ログイン/別ユーザーを拒否。HOME版のサービスワーカー登録は行わず、ログアウト後にオフラインキャッシュで表示しない。

旧 https://cetus.fun/muscle-bank/ は独立の端末保存版のまま。旧端末データに新HOMEから直接アクセスはできない。旧版の設定でバックアップ→HOME版の設定で復元すると、ママ本人の新クラウド記録として移行する。旧版にHOMEのCookieを渡さず、旧APIや旧URLから新データを取得できない。

## おじいちゃんの食事チェック（2026-10-04）

`/apps/kidney/` と `/api/kidney` をHOMEセッションで保護。migration 0008は食品記録・設定の専用テーブルを追加する。既存の食事記録や検査値を移行・投入しない。家庭ごとに1つの家族共通食事帳を持ち、同じhouseholdのメンバーが登録・閲覧できる。複数家庭に所属する人は家庭を選択する。別家庭・脱退したアカウントからの読取・更新は拒否。

食品候補は端末内の未確定予定。確定時に記録を1件ずつ保存し、別端末の記録をまとめて上書きしない。再送は同じIDを使用。栄養量・食品名・量を記録に保存し、食品マスタの将来変更で過去の合計を変えない。自分の記録は変更・取消可能。家庭owner/adminは全員の記録を変更でき、共通目標量の設定もできる。変更にはrevisionを用い、競合時は読み直しを案内する。開いている画面は15秒ごとと再表示時に同期。

初期目標は仮の表示。設定済みになるまでは余裕・注意などの上限判定をしない。検査値から上限を自動決定しない。食品BOOKの登録済み67件を利用し、未登録食品・独自料理・糖分/脂質等の追加は別途対応が必要。旧Sites版の端末記録は自動移行しない。

HOME設定の「おじいちゃん向け：2つだけにする」は現在のアカウントにだけ適用。他の家族の表示設定・アクセス権を変更しない。カレンダーは既存 `https://cetus.fun/kanriapp/calendar.html` への認証済み入口のみ。カレンダーのHOME認証への移行は行わず、旧合言葉・プロフィールと予定データを維持する。新しい端末ではカレンダーの初回ログインが必要。

人型ゲージは `public/apps/kidney/shape-fill-gauge.js` の `ShapeFillGauge` に分離。`key/label/color/max/shapePath/templateSelector/onSelect` を設定し、`update(現在量,予定量,選択中)` で描画する。shapePathは90×150の座標系で差し替え可能。確定層と予定層が下から0.72秒で満ち、予定だけ斜線になる。こども版の既存公開コードは今回変更しない。

## 大人の家族の招待（2026-10-04 修正）

HOME設定の上部に「大人の家族を招待」。householdのowner/adminはplatform_roleがuserでも、自分の家庭へ招待を発行できる。sharingグループの発行は従来どおりoperatorかつ当該グループowner/adminに限定。一般メンバー・別家庭の管理者は発行できない。取消は発行本人かつ現在も当該グループの管理者のみ。子ども用招待も家庭管理者が発行可能。

大人の招待はchild_idを指定しない既存の招待経路。登録時のroleはmember、platform_roleはuser。children行を追加・連携しない。既存の姉妹アカウント・家庭表示設定・栄養目標は変更しない。コードは1人1回・7日間・取消可能。
