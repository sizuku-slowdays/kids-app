## 画面・権限

URLは既存 https://cetus.fun/wagaya/apps/passbook/ のまま。

- 申請者：同じ家庭の、明示的に「大人」と設定されたHOMEユーザー。家庭のowner/adminも子ども区分・children登録がなければ対象。氏名・人数を固定しない。「不明」は通常メンバーには申請権を与えない。
- 受取候補：同家庭で有効なHOMEアカウントとメンバー登録を持ち、既存のcash/chores通帳がある子ども。候補には名前と利用できる通貨だけを返し、残高・他の人からの申請は返さない。
- 承認者：既存HOME上の同家庭owner/adminを保護者権限とする。子ども区分・children登録・無効ユーザーは除く。新しい親子認証モデルや氏名による推測はしない。申請者本人の自己承認は禁止。別の承認者がいない場合は申請不可。
- 保護者は「申請できる家族の設定」で子どもごと・申請者ごとに許可を外せる。既定は同家庭の大人を許可。拒否された申請者の未処理申請も承認時に再検証、却下は可能。
- 子どもには本人が受け取った承認済みプレゼントだけを返す。姉妹のポイント共有設定がONでも、gift APIで他の子の申請・理由は返さない。
- 祖父母は自分のpending/approved/rejectedだけを確認できる。本人通帳のない通常大人はプレゼント専用画面になり、従来の残高/履歴/当番APIへのアクセスを拒否。本人の大人通帳がある場合はその従来機能を維持。他の子の残高閲覧権は与えない。
- 他家庭の子への申請は今回は開放しない。household_id、child_id、sender_id、resolved_by、子ども別許可を分離して保存するので、将来の相互許可APIを追加できる。現在の同家庭制限を無断で緩めない。

## DB・二重加算防止

`0021_passbook_gifts.sql` は追加のみ。既存表のUPDATE/DELETE・既存台帳再計算・初期化なし。

| 新規オブジェクト | 用途 |
| --- | --- |
| passbook_gift_requests | 不変の申請内容・申請者ID/表示名の記録・受取人・account・通貨・理由・状態・確認者ID/日時 |
| passbook_gift_permissions | 子ども×申請者の許可設定と変更者 |
| passbook_gift_notifications | 宛先ごとの永続送信待ち・リース・試行回数・送信結果 |
| passbook_gift_guardians / passbook_gift_senders（view） | 現在のHOME権限の共通判定 |
| gift_push_deliveries（通知DB・別SQL） | 申請通知ID×端末endpointごとの成功済み配信記録 |

- ブラウザのevent_idを家庭×申請者で一意化。再送は同一payloadのみ受け入れる。申請者名・確認者・家庭をブラウザから指定できない。
- INSERT時と承認UPDATE時のDBトリガーでも家庭・区分・対象・許可・保護者を検証する。
- 申請INSERTと承認者への通知outbox作成は同じSQL内。承認UPDATEと台帳INSERTもトリガーにより同じトランザクション。加算が失敗すれば申請はpendingに戻る。
- `passbook_entries` に source_app=`gift`、source_event=申請IDで一意加算。承認の二重クリック・同時実行・通信失敗後の同じ承認リトライは加算1回。処理済みの別結論は409。
- 金額は1〜10,000,000の整数。理由は1〜500文字。実際の承認時点を入金日時にする。既存の利息開始日・日次残高・お小遣い処理は変更しない。
- 現金のdestinationはbank、ポイントはpoints。walletという将来の宛先区分は保持するが、今回はサーバー/トリガーで利用を拒否する。
- 寄贈者の口座から引落は行わない。現金受け渡し・立替・精算済みを示す状態は設けない。画面にその区別を明記する。
- 申請履歴は削除しない。承認後の取り消し/返金UIは今回対象外。既存の手動調整を使う場合も新しい履歴を追記し、元の申請・台帳を消さない。

## 通知

申請直後に保護者へHOME Pushを試みる。未登録端末・一時障害は申請を消さずpendingに保存し、保護者の再送ボタンと既存HOME Cron（金融処理の後）で再試行する。既存の通知ルール・購読・カレンダー・学校準備通知に書き込まない。

通知Workerの専用内部ルートからHOMEに問い合わせ、現在のpending状態・家庭保護者・有効な端末セッションを毎回検証。外部公開ホストから内部ルートは利用不可。旧recipient/allへのフォールバックなし。通知本文に氏名・金額・理由を含めない。通知から既存通帳の申請画面を開く。

端末ごとに成功した送信は再試行で省略し、失敗した端末だけ再送。同じtagを使用。ただしPush受付後からDB成功記録前のプロセス停止による二重表示まで、外部PushとD1間で厳密なexactly-onceは保証できない。通知の重複が残高の二重加算を起こすことはない。

申請時点の承認対象へ通知を作成する。後から保護者になった人も現在の権限で未処理申請を一覧・承認できるが、過去申請について新任者へ通知を自動再発行する機能は今回対象外。
