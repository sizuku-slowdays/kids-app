# つうちょう：複数人・複数回・過去日のお手伝い

調査基準：HOME正本 `338aee5b2d60c806389f3ce9bd830c61ffa49c56`。2026-10-28 JST。独立作業ブランチで準備し、本番反映は最新バックアップ確認後。

## 挙動

- お手伝い1種類を複数人で完了できる。選んだ人それぞれへ現在の設定報酬を付与する（分割払いではない）。
- 1人あたり1〜100回を指定でき、同じ日のお手伝いを追加登録できる。登録済みのお手伝いも一覧・選択肢から消さない。
- 作業日を今日以前の日付から選択し、その日の完了一覧を確認できる。未来日・実在しない日をAPIで拒否。
- 過去日を指定しても、通帳への加算日時は実際の処理日時。メモに作業日と回数を残す。過去残高や確定済みの利息を遡及修正しない。過去の報酬設定は推測せず、画面に現在の設定額を表示する。
- 登録できるのは家庭のowner/admin。子どもや一般大人が直接APIで加算することも拒否。別家庭の人は選べない。

## 保存と再処理

追加migration `0025_passbook_chore_records.sql`：`passbook_chore_records`（作業日・人の配列・回数・報酬スナップショット・登録者）と `passbook_chore_record_payments`（一意な支払確定）。既存テーブルの作り直し・既存行の移動/再加算は行わない。

既存 `passbook_chore_days` と `passbook_chore_attempts` の1日1件制約はそのまま。旧クライアント/旧未払い精算を壊さず、新記録を別の追加表で表現する。旧表には登録番号の相互再利用を防ぐ追加BEFORE INSERTガードのみ付ける。既存トリガー定義は変更しない。

新しい登録は `POST /api/passbook/chores/records`。家庭×event_idを一意とし、日・人・回数の違う再送は拒否。同じ登録の再試行は同じsnapshotを使う。画面では最初の送信後の内容を固定し、通信失敗後に別の数量で再送しない。意図した追加登録は新しい登録番号を作る。

支払確定1 INSERTのDBトリガーから、既存の子ども/大人のポイント・現金台帳へ同時加算する。どれか1人の通帳不足や途中エラーでも、全員分の金融書込・支払確定・当番更新がロールバック。元の未払いsnapshotは保持し、保護者が `POST /api/passbook/chores/records/retry` で再処理できる。再処理までに報酬設定が変わっても、元のsnapshotを使用する。

当日の最初の完了だけ現在の当番を翌日に進める。追加分・過去分はその日の現在の当番を動かさない。表示には旧完了・旧未払い精算・新しい完了をまとめる。おさいふ・いいことポイント・交換・お小遣い/利息処理・通知・R2に新たな連携/移行はしない。

## 反映ゲート

1. 利用者PCで `scripts/check-chore-records-rollout.ps1 -SourceCommit <固定SHA> -Mode backup`。home-dbを新しい日時別フォルダへSQL exportし、PythonでSQLite integrity/FKとschemaを確認。新表が既にあるbefore、保存先重複、失敗は停止。SQLやPRIVATEファイルはチャットへ送らない。
2. BACKUP ALL OKの確認後、HOME正本の先頭が調査版から変わっていないことを再確認して統合。既存のGit自動反映（home-db migrations apply→home-worker deploy）を使用。手動で残高を更新しない。
3. 使い始める前に、同じスクリプトを `-Mode verify -Folder <同じフォルダ>` で実行。既存passbook/いいこと台帳・ユーザー/家庭/所属/子どもと旧SQL定義の一致、新2表が空を確認。差があればリセットせず内容を確認する。
4. 保護者でつうちょうを更新し、新しい日付欄・複数人・回数を確認。既存の本番残高で試験用の加算を行わず、実際に行ったお手伝いだけ登録する。

export中はD1が一時的に照会へ応答できないことがあるため、利用が少ない時間に実施する。バックアップスクリプトはmigration/Deploy/入金/設定変更を実行しない。元に戻す場合も追加した台帳を削除せず、まずWorkerだけの切戻しを検討する。
